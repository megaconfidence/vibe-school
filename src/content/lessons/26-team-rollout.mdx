Getting one person productive with Vibe is a setup job. Getting a team productive is a rollout: everyone should start from the same instructions and workflows, with the same guardrails, and you should be able to tell whether it's working. This lesson is for team leads and Change Champions. It covers what goes in the repository, what admins set centrally, what to measure, and a checklist for the first few weeks.

## In your project

This is the capstone for `vibe-todo`. By now it holds a full team setup, built one lesson at a time:

```text
vibe-todo/
├── AGENTS.md                          # Instructions
├── README.md                          # gains a "Working with Vibe" section in this lesson
├── tests/AGENTS.md                    # Instructions
└── .vibe/
    ├── config.toml                    # Configuration, Permissions, MCP, Agents
    ├── hooks.toml, hooks/run_tests.py # Hooks
    ├── agents/builder.toml, reviewer.toml          # Agents
    ├── skills/new-command/, skills/code-review/    # Skills
    └── plugins/todo-review/           # Plugins
```

In this lesson you review it the way a teammate would, compare it with the [reference project](/examples/agents-skills-instructions) (where `vibe-todo` stands after the Agents lesson: instructions, skills, and agents), add a README note about trusting the folder, draft the admin config that would back it, and optionally push it to a team repository.

## Layer 1: share the setup through the repo

Everything above is ordinary files in the repository. Anyone who clones it and trusts the folder gets the same agents, skills, instructions, hooks, and MCP server in the CLI and the VS Code extension. Desktop local sessions use the same engine, but tools and prompts can differ, so test there too.

Before you share it, check what a teammate would get:

- `git ls-files AGENTS.md tests/AGENTS.md .vibe` lists exactly what's shared.
- The project config holds team choices only. Personal settings such as `theme` or `active_model` stay in each person's `~/.vibe/config.toml`.
- Allowlists name harmless commands, and hooks call tools teammates have installed.

## Layer 2: admin config

Repo files are opt-in: they apply in that repo, once trusted. **Admin config** (also called managed config) applies to everyone in an Organization or Workspace, in every project. Admins write it once as TOML, and the CLI and VS Code extension apply it.

### How it works

1. An admin enters TOML under **Vibe Code Clients managed config**, in **Admin Panel › Vibe › Preferences** for the Organization, or in a Workspace's **Settings**.
2. The client fetches it with the user's Mistral API key and keeps a copy in `~/.vibe/managed_config_cache.json`. It checks for changes every 10 minutes; `/reload` fetches it right away. It never writes admin config into `config.toml`.
3. Admin-managed settings show as read-only in `/config`, with the administrator listed as a source.

A Workspace can inherit the Organization's config, **replace** it with its own (the two aren't merged), or turn admin config off for its members. Managing it needs the `manage_code_config` permission at the Organization scope; Workspace admins can manage their own Workspace's config.

**Minimum versions:** CLI `2.24.2`, VS Code extension `1.16`. Older clients ignore admin config, so upgrade everyone first. **Activation:** nothing to do on Serverless; on Dedicated or Self-hosted deployments, ask your account team.

### Precedence

Admin config is the top layer:

```text
admin config  >  agent settings  >  CLI flags  >  VIBE_* env vars  >  project config.toml  >  user config.toml
```

### What admins can set

Most `config.toml` keys work. The ones a rollout usually needs:

```toml
# Everyone starts in a safe agent, and auto-approve is off the menu
default_agent = "accept-edits"
disabled_agents = ["auto-approve"]
enable_auto_approve = false

# Only these models are selectable
allowed_models = ["mistral-vibe-cli-*"]

# No MCP servers, and no web search connector
enable_mcp = false

[[connectors]]
name = "web_search"
disabled = true
```

| Key | Effect |
|---|---|
| `active_model`, `[[providers]]`, `[[models]]` | Ship a working model and provider on first launch, for example your enterprise endpoint |
| `allowed_models` | Limits the model picker to names matching exact, glob, or `re:` patterns. If no model matches, the **whole** admin config is rejected |
| `default_agent`, `enabled_agents`, `disabled_agents` | The agent every session starts in, and which ones users can switch to |
| `enable_auto_approve = false` | Hides `auto-approve` and any agent with `safety = "yolo"`, and ignores `--auto-approve`, `--yolo`, and `bypass_tool_permissions`. Per-tool `always` and allowlists still apply |
| `enable_mcp = false` | Blocks adding, signing in to, and loading tools from MCP servers, including plugin ones |
| `enable_connectors = false` or `[[connectors]]` with `disabled = true` | Blocks all [connectors](/glossary#connector), or one |
| `disabled_tools` | Removes tools, for example `["bash"]` |

Admin config never holds a literal secret: credentials must be an environment variable reference, such as `api_key_env_var = "MISTRAL_API_KEY"`. The server rejects literal keys. To stop applying admin config, submit an empty configuration. Test it in a test Organization first: if it can't be applied, users fall back to the last one they received, then to their own config, with the message `Your administrator-managed configuration could not be applied: <reason>`.

<div class="callout">
Admin config is a <strong>distribution mechanism, not a security control</strong>. It sets safe defaults, but someone who controls their own machine can get around it. Anything people must never reach also needs a server-side control, such as Workspace permissions or API key scope.
</div>

## Layer 3: the Admin Panel

The [Admin Panel](https://admin.mistral.ai) is where an Organization admin or Workspace admin manages people, access, and spend. You need one of those roles to open it. The parts that matter for a Vibe rollout:

- **Workspaces.** An Organization contains Workspaces, each with its own members, roles, API keys, usage, and limits. Everything in Vibe is Workspace-scoped. Per Workspace, admins can turn Vibe features on or off (Work mode, Web Search, Code Interpreter, and others) and set a chat retention policy. A separate Workspace for the pilot keeps its usage and settings apart.
- **Roles.** Roles apply at the Organization scope and the Workspace scope, and they add up. New Workspace members start as **Workspace Contributor**. The **Mistral Vibe Code User** role (`mistral_code_user`) grants Mistral Code access and requires a seat.
- **Groups and SCIM.** On Enterprise plans, a **group** assigns many users to a Workspace with chosen roles. **SCIM provisioning** (private preview) syncs users and groups from your identity provider, such as Microsoft Entra ID.
- **Usage and limits.** Each Workspace has a **Usage** tab (spend, tokens, usage by model) and an optional **Monthly spending limit** under **Settings**. On Enterprise plans, the Admin API also reports Vibe Code analytics: sessions, active users, tokens, tool calls, and session durations.
- **API keys vs service accounts.** API keys belong to the Workspace they were created in and use its quota. Use a personal key for interactive work, and a **service account** (a non-human identity with its own roles and credentials) for workloads, so they keep running when a person leaves.
- **Connectors.** Under **Administration › Connectors**, admins set each connector to **Allowed**, **Restricted** (selected tools only), or **Blocked** per Workspace, and can connect GitHub or Slack once for the whole Organization.

Each of these has more detail in the [Admin docs](https://docs.mistral.ai/admin/overview): [Workspaces in Vibe](https://docs.mistral.ai/admin/workspaces/workspaces-in-vibe), [roles and permissions](https://docs.mistral.ai/admin/identity-access/roles-permissions), [groups](https://docs.mistral.ai/admin/identity-access/groups), [SCIM](https://docs.mistral.ai/admin/identity-access/scim/overview), [Workspace usage and limits](https://docs.mistral.ai/admin/workspaces/usage-limits), [usage metrics API](https://docs.mistral.ai/admin/admin-api/usage-metrics), [API keys](https://docs.mistral.ai/admin/identity-access/api-keys), [service accounts](https://docs.mistral.ai/admin/identity-access/service-accounts), and [connectors](https://docs.mistral.ai/admin/identity-access/connectors).

## Observability

To see what agents do across the team, Vibe can export **OpenTelemetry** traces for agent, model, and tool operations over OTLP/HTTP:

```toml
enable_otel = true
otel_endpoint = "https://collector.example.com:4318"
otel_redaction = "default"
```

- `enable_otel` needs `enable_telemetry` on as well.
- Without `otel_endpoint`, Vibe derives the endpoint from the configured Mistral provider. With it, Vibe sends to `<otel_endpoint>/v1/traces`; set collector auth with the standard `OTEL_EXPORTER_OTLP_*` environment variables.
- `otel_redaction`: `default` redacts sensitive values, `strict` drops sensitive attributes entirely, and `none` turns redaction off. Use `none` only with a collector you trust with prompts, responses, and tool data.

Separately, `enable_telemetry` (default `true`) sends anonymous usage and error telemetry to Mistral. No prompts, file contents, or model outputs are sent. Set `enable_telemetry = false` to opt out, for example for offline-only setups.

## A rollout checklist

1. **Pick a pilot group.** A handful of people on one or two repos, ideally in their own Workspace so usage is easy to read.
2. **Commit the shared setup.** `AGENTS.md`, `.vibe/config.toml`, and one or two skills that match how the team already works, as in `vibe-todo`. Add a README note about trusting the folder.
3. **Set guardrails.** Start everyone in `accept-edits` or `ask`, consider `enable_auto_approve = false` and `allowed_models` in admin config, and back them with Workspace roles and connector permissions.
4. **Measure usage.** Watch the Workspace **Usage** tab and spending limit; on Enterprise, pull Vibe Code analytics; add OpenTelemetry if you run a collector.
5. **Gather feedback, then widen.** Ask which rules the agent ignored, which skills got used, and what people still did by hand. Fix the shared setup, then add the next group.
