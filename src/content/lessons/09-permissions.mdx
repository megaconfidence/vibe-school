Vibe can read files, edit code, and run shell commands on your behalf. You decide how much it does on its own. Three layers control that: the active [agent](/glossary#agent) sets how often Vibe asks, [trusted folders](/glossary#trusted-folder) decide whether a project's own config loads, and per-tool rules tighten or loosen individual tools.

## In your project

This lesson lets Vibe run the `vibe-todo` tests without asking, and makes sure the folder is trusted:

```text
vibe-todo/
└── .vibe/
    └── config.toml    # adds [tools.bash] allowlist with "python3 -m unittest"
```


## Agents set the approval level

| Agent | What it approves on its own | Use for |
|---|---|---|
| `ask` | Nothing. Asks before every tool. | Unfamiliar code, or when you want to vet each action. |
| `accept-edits` | **Default.** File edits. Still asks for shell commands and other sensitive tools. | Day-to-day work and scoped refactors. |
| `smart-approve` | Calls a model judges safe. Asks before risky ones. | Day-to-day work with fewer prompts. |
| `auto-approve` | Everything, including shell commands. | Disposable, sandboxed environments only. |

`smart-approve` is a classifier, not a sandbox: a call it judges safe runs with your user's full access. For untrusted code or sensitive credentials, use `ask` or an isolated environment.

Whatever the agent, Vibe also asks before a tool reads, writes, or runs something **outside the working directory**, and before it touches `.env` or `.envrc` files. Only `auto-approve`, or a path in the tool's `allowlist`, skips those checks.

## Trusted folders

A project can ship its own Vibe setup in `.vibe/` (config, agents, skills, prompts, plugins), plus `.agents/skills/` and `AGENTS.md`. Because that changes how Vibe behaves, it only loads from folders you trust.

The first time you start Vibe in such a folder, it lists what it found and offers **Trust folder**, **Trust full repo** (when you start in a subfolder of a git repository), or **Don't trust**. Review those files first, especially MCP servers and tool permissions.

- Decisions are stored in `~/.vibe/trusted_folders.toml`.
- `/trusted-folders` in the CLI lets you browse, change, or forget them. Changes apply the next time Vibe starts.
- `vibe --trust` trusts the working directory for a single run. Programmatic mode (`vibe --prompt`) never asks, so use `--trust` there.

You trusted `vibe-todo` at the end of the [Configuration](/lessons/configuration) lesson, because its `.vibe/` folder made Vibe ask.

## Per-tool rules

In `config.toml`, each tool can have its own block. `permission` is `"always"`, `"ask"`, or `"never"`:

```toml
[tools.read_file]
permission = "always"

[tools.write_file]
permission = "never"

[tools.bash]
permission = "ask"
allowlist = ["ls", "pwd", "cat", "git status", "git diff", "git log", "npm test"]
denylist = ["rm -rf"]
```

For `bash`, `allowlist` and `denylist` match command prefixes. Some read-only commands (`ls`, `pwd`, `cat`, `git status`, and others) are allowed by default, and **setting a list replaces its defaults**, so include the ones you want to keep.

In `vibe-todo`, the project file gets its own list, so the tests run without a prompt for anyone who trusts the folder:

```toml
# vibe-todo/.vibe/config.toml
default_agent = "accept-edits"

[tools.bash]
allowlist = ["ls", "pwd", "cat", "git status", "git diff", "git log", "python3 -m unittest", "python3 -m todo"]
```

A project list replaces your user list for that project; it doesn't add to it. On Windows, use the command name that works there (often `python`). If your shell tool is `git_bash` or `powershell` instead of `bash`, put the list under `[tools.git_bash]` or `[tools.powershell]`.

Other controls:

- **Sensitive files**: `sensitive_patterns` makes a file tool ask before touching matching paths (default: `.env` and `.envrc` files). Setting it replaces the defaults. See [sensitive file protection](https://docs.mistral.ai/vibe/code/cli/configuration-reference#sensitive-file-protection).
- **Outside the working directory**: `outside_workdir = "deny"` refuses instead of asking, at the top level or per tool.
- **Turn tools on or off**: `enabled_tools` and `disabled_tools` take exact names, globs, or `re:` regexes, for example `disabled_tools = ["bash"]`.
- **MCP and connector tools** use the same blocks. MCP tools are named `server_tool`, for example `[tools.fetch_server_get]`. More in [MCP](/lessons/mcp).

<div class="callout">
Your organization's admin can set <code>enable_auto_approve = false</code>. That hides the <code>auto-approve</code> agent and makes Vibe ignore <code>--auto-approve</code> and <code>--yolo</code>. Per-tool permissions still apply.
</div>

## Good habits

- Commit before risky runs, so you can roll back.
- Start in `ask` on code you don't know.
- Keep `auto-approve` for containers, CI runners, and throwaway VMs, never on a machine with SSH keys or cloud credentials.
- Keep tools that touch external systems on `permission = "ask"`.

Learn more in [Safety, approvals, and permissions](https://docs.mistral.ai/vibe/code/safety-approvals-permissions).
