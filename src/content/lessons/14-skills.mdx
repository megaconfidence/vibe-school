A [skill](/glossary#skill) is a set of instructions for one job, like writing a commit message or reviewing a pull request, saved in a `SKILL.md` file. The model sees each skill's name and description, and loads the full instructions only when it needs them. Skills also become your own slash commands: write it once, then type `/new-command` whenever you want it.

Vibe follows the [Agent Skills specification](https://agentskills.io/specification), so a skill you write here also works in other agents that use the same format.

## In your project

This lesson adds two project skills to `vibe-todo`, then uses the first one to add a `remove` command:

```text
vibe-todo/
├── .vibe/
│   └── skills/
│       ├── new-command/SKILL.md   # new: how to add a subcommand and its test
│       └── code-review/SKILL.md   # new: review checklist and output format
├── todo/cli.py                    # gains cmd_remove
└── tests/test_cli.py              # gains test_remove and test_remove_unknown_id
```


## The SKILL.md format

A skill is a folder with a `SKILL.md` file inside. The file starts with YAML frontmatter, then the instructions in Markdown:

```markdown
---
name: new-command
description: Add a new subcommand to the todo CLI, with its test. Use when the user asks for a new todo command such as remove, clear, edit or stats.
user-invocable: true
---

# Add a new todo subcommand

1. Read `todo/cli.py` and `tests/test_cli.py` to see the existing pattern.
2. Add a `cmd_<name>(args: argparse.Namespace) -> int` function. Load tasks with `store.load()`, save them with `store.save()`.
3. Register it in `build_parser()` with `sub.add_parser("<name>", help="...")` and `set_defaults(func=cmd_<name>)`.
4. Add a success test with the `run_cli` helper, plus an unknown-id test if the command takes a task id.
5. Run `python3 -m unittest`. Fix anything that fails.
```

On Windows, write `python -m unittest` in the skill if `python3` isn't on your path.

| Field | What it does |
|---|---|
| `name` | Lowercase letters, digits, and hyphens. Match the folder name |
| `description` | What the skill does and when to use it, up to 1,024 characters. The model reads this to decide when to load it |
| `user-invocable` | Defaults to `true`, which makes it a `/skill-name` command. `false` hides it from the `/` menu; the agent can still load it |
| `disable-model-invocation` | `true` stops the agent loading it on its own. You can still run it with `/skill-name` |
| `allowed-tools` | Lists the tools the skill expects. Vibe reads it but **doesn't enforce it** |

<div class="callout">
<code>allowed-tools</code> doesn't restrict anything. To limit what a skill can do, restrict the tools and permissions of the agent that runs it (see <a href="/lessons/permissions">Permissions</a> and <a href="/lessons/agents">Agents</a>).
</div>

## Where skills live

Vibe searches these locations, in order:

1. Paths in `skill_paths` in `config.toml`
2. `.vibe/skills/` and `.agents/skills/` in your project, when the folder is [trusted](/glossary#trusted-folder)
3. `~/.vibe/skills/` and `~/.agents/skills/`, for every project

Put personal skills in `~/.vibe/skills/`. Put project skills in `.vibe/skills/` and commit them, so your team reviews and shares them. Both `vibe-todo` skills are project skills: they only make sense in that repository.

[Plugins](/lessons/plugins) can ship skills too. Their names get the plugin's prefix, like `/vibe:skill-creator`.

## Use a skill

Type `/` and pick the skill, then add your request:

```text
/new-command add a remove command that deletes a task by id
```

In the `/` menu, each skill's description starts with its scope: `project`, `user`, or `vibe`. A skill named like a built-in command isn't listed.

You don't always have to call it: if your request matches a skill's description, the agent can load it on its own.

## Manage skills

<SurfaceTabs>
<SurfaceTab surface="cli">

Run `/skills` to list your installed skills with their scope and source, and to read the highlighted one. Press `/` to search and `Space` to turn a skill on or off. Vibe updates `disabled_skills` for you.

A running session picks up new or edited skills on its own. If a change doesn't show up, run `/reload`.

</SurfaceTab>
<SurfaceTab surface="vscode">

The extension reads the same skill folders as the CLI. Skills that are `user-invocable` appear in the extension's `/` picker. Type `/reload` in the Vibe panel after adding one.

</SurfaceTab>
<SurfaceTab surface="desktop">

Local sessions in Vibe Desktop share the CLI's core engine, but tools and prompts can differ. After you add or edit a skill, start a **New Session** in the **Code** tab, then ask for the skill by name (or type `/` if your version lists skills there). To manage skills, edit the folders above or run `/skills` from the CLI.

</SurfaceTab>
</SurfaceTabs>

To filter skills in `config.toml`, use patterns (exact names, globs, or `re:` regex):

```toml
enabled_skills = ["new-command", "code-review"]
disabled_skills = ["experimental-*"]
```

If `enabled_skills` isn't empty, only matching skills load. Otherwise every skill loads except those matching `disabled_skills`.

Vibe no longer loads custom Python tools. To teach Vibe a new workflow, write a skill. To connect it to an outside service, add an <a href="/lessons/mcp">MCP server</a>.
</div>
