[Hooks](/glossary#hook) run your own shell commands at fixed points in a Vibe session: before a tool runs, after it runs, when you send a message, when the agent finishes. Use them to block dangerous commands, format files after every edit, load context at startup, or ping you when Vibe needs you. Unlike instructions in `AGENTS.md`, a hook always runs: the model can't forget it.

## In your project

This lesson adds a project hook to `vibe-todo` that runs the tests after every Python edit and tells the agent when they fail:

```text
vibe-todo/
└── .vibe/
    ├── hooks.toml          # new: run-tests, a post_tool hook on edit and write_file
    └── hooks/
        └── run_tests.py    # new: runs python3 -m unittest, reports the result
```


## Where hooks live

Hooks go in a `hooks.toml` file, separate from `config.toml`:

- **Project**: `./.vibe/hooks.toml` in the working directory. Loaded first, and only in a [trusted folder](/glossary#trusted-folder).
- **User**: `~/.vibe/hooks.toml`. Loaded second, applies everywhere.

If both files declare a hook with the same `name`, the project one wins. Subagents inherit the parent's hooks, so a policy also covers work they do. A [plugin](/lessons/plugins) can ship hooks too.

## Declare a hook

Each hook is a `[[hooks]]` table:

```toml
[[hooks]]
name = "deny-rm-rf"
type = "pre_tool"
match = "re:bash|process_start"
command = "python3 .vibe/hooks/guard-bash.py"
timeout = 60.0
strict = true
description = "Reject dangerous shell commands."
```

| Field | Required | Details |
|---|---|---|
| `name` | yes | Unique identifier. |
| `type` | yes | The event, see below. |
| `command` | yes | Shell command to run. Receives the payload on `stdin`. |
| `match` | no | Glob, or regex with `re:`. Case-insensitive. Default: everything. |
| `timeout` | no | Seconds before the hook is killed. Default `60`. |
| `strict` | no | For `pre_tool`, `post_tool`, `pre_agent`, `pre_llm`, `post_llm`: turn failures into denials, cleared output, blocked messages, or an ended turn instead of warnings. |
| `description` | no | Shown in diagnostics. |

## Events

| Type | When it fires | `match` selects | Can do |
|---|---|---|---|
| `pre_tool` | Before each tool call, before the permission prompt | Tool name (`bash`, `file_system.bash`) | Deny the call, or rewrite its arguments |
| `post_tool` | After a tool actually ran | Tool name | Replace or append to the output the model sees |
| `pre_agent` | After you send a message, before the model reads it | Agent name (`main` for the main agent) | Block the message, rewrite it, or add context |
| `pre_llm` | Before each call to the model (several times per turn when tools run, so keep it fast) | Agent name | Deny to stop the turn |
| `post_llm` | After each model response, before Vibe acts on it | Agent name | Deny to discard the response and ask the model to try again |
| `post_agent` | After a turn ends with no pending tool calls | Agent name | Deny to ask the agent to retry |
| `notification` | Vibe needs you or a turn ends | `approval_requested`, `question_asked`, `turn_completed`, `turn_failed` | Nothing: runs in the background, output ignored |
| `session_start` | A session starts | `startup`, `resume`, `clear`, `fork` | Add context for the model |
| `session_end` | A session ends | `exit`, `clear`, `other` | Nothing: runs in the background |

`post_llm` and `post_agent` share one budget of 3 retries per turn. Past it, the response is accepted.

<div class="callout">
Commands the agent starts in the background go through <code>process_start</code>, not <code>bash</code>. Shell guards should use <code>match = "re:bash|process_start"</code>.
</div>

## The contract

Vibe starts the hook with a JSON object on `stdin`: `session_id`, `parent_session_id`, `transcript_path`, `cwd`, `hook_event_name`, plus the event's own fields (for `pre_tool`: `tool_name`, `tool_call_id`, `tool_input`).

The hook answers with its **exit code** and **stdout**:

| Exit and stdout | Effect |
|---|---|
| Exit `0`, empty stdout | Pass through. |
| Exit `0`, a JSON object | Vibe acts on its fields. |
| Exit `0`, anything else | Failure: a warning, or a denial with `strict = true`. |
| Non-zero exit or timeout | Failure. The reason comes from `stderr`, then `stdout` if `stderr` is empty, then the exit code. |

The JSON fields:

```json
{
  "decision": "deny",
  "reason": "rm -rf is not allowed here.",
  "system_message": "Blocked a dangerous command."
}
```

`decision` defaults to `"allow"`. On a `pre_tool` deny, `reason` becomes the tool error the model sees. `system_message` is shown to you only. `hook_specific_output` holds event-specific fields: `tool_input` (`pre_tool`), `prompt` (`pre_agent`), or `additional_context` (`post_tool`, `pre_agent`, `session_start`). Use `stderr` for logs.

## Examples

**Run the tests after each edit.** This is the `vibe-todo` hook. It fires after `edit` or `write_file` runs, and only acts on Python files:

```toml
# vibe-todo/.vibe/hooks.toml
[[hooks]]
name = "run-tests"
type = "post_tool"
match = "re:edit|write_file"
command = "python3 .vibe/hooks/run_tests.py"
timeout = 60
description = "Run the vibe-todo tests after each Python edit."
```

```python
# vibe-todo/.vibe/hooks/run_tests.py
import json, subprocess, sys
from pathlib import Path

payload = json.load(sys.stdin)
if payload.get("tool_status") != "success":
    sys.exit(0)
path = Path((payload.get("tool_input") or {}).get("file_path", ""))
if path.suffix != ".py":
    sys.exit(0)

result = subprocess.run(
    [sys.executable, "-m", "unittest", "-q"],
    cwd=payload["cwd"], capture_output=True, text=True,
)
if result.returncode == 0:
    print(json.dumps({"system_message": "vibe-todo tests pass"}))
else:
    print(json.dumps({"hook_specific_output": {
        "additional_context": "The test suite fails after this edit:\n" + result.stderr[-2000:]
    }}))
```

When the tests pass, the CLI shows a short message and the model sees nothing extra. The VS Code extension doesn't display a hook's `system_message`, so there a passing run is silent. When they fail, the failure is appended to the tool output the model reads, so it can fix the problem in its next step. Hooks run in the session's working directory, so start Vibe in the project root. On Windows, use `python` in `command`; hooks run in Git Bash when it's installed, otherwise PowerShell.

**Format after each edit.** The [hooks documentation](https://docs.mistral.ai/vibe/code/cli/hooks#example) has a similar `post_tool` hook that runs Ruff and tells the agent when a file changed.

**Get notified.** Hear when Vibe needs approval or finishes:

```toml
[[hooks]]
name = "notify-me"
type = "notification"
match = "re:approval_requested|turn_completed"
command = "say 'Vibe needs you'"
```

**Load context at startup.** Feed a file to the model at the start of each new session:

```toml
[[hooks]]
name = "load-context"
type = "session_start"
match = "startup"
command = "jq -Rs '{hook_specific_output: {additional_context: .}}' .vibe/context.md"
```

## Where hooks run

<SurfaceTabs>
<SurfaceTab surface="cli">

The CLI reads both `hooks.toml` files when a session starts. Start a new session after you edit them. Config errors, such as invalid TOML or a missing field, show up as warnings and the broken hook is skipped.

</SurfaceTab>
<SurfaceTab surface="vscode">

The extension shares `~/.vibe/` and project `.vibe/` folders with the CLI, so the same `hooks.toml` files apply. Start a new conversation with `Mod+N` after editing them.

</SurfaceTab>
<SurfaceTab surface="desktop">

Desktop local sessions share the CLI's core engine. Hooks also see Desktop events: `session_end` fires with `exit` when Desktop archives a session. Start a new session after editing `hooks.toml`.

</SurfaceTab>
</SurfaceTabs>

Learn more in the [hooks documentation](https://docs.mistral.ai/vibe/code/cli/hooks).
