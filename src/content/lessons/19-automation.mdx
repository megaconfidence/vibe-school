So far you've worked with Vibe in a conversation. The CLI can also run with no one watching: one prompt in, one result out, ready for a shell script, a cron job, or a CI pipeline. And inside a session, it can repeat a prompt on a schedule or keep chasing a goal until it's done.

## In your project

No new files are required. You'll run `vibe -p` in `vibe-todo` to run the tests and report the result, with the `builder` agent's allowlist and no file tools:

```bash
cd ~/vibe-school/vibe-todo
vibe --trust -p "Run python3 -m unittest and report the result in one sentence. Do not edit any file." \
  --agent builder --enabled-tools bash --max-turns 5 --output json > ../vibe-run.json
```

Optionally, if you've pushed the project to GitHub, add a workflow under `.github/workflows/` that does the same on every pull request.


## Programmatic mode

Pass `-p` (or `--prompt`) to run a single task and exit:

```bash
vibe -p "Analyze the codebase" --max-turns 5 --output json
```

You can also read the prompt from a file with `--prompt-file PATH`, or pipe it on stdin with `-p` and no text.

Programmatic mode has no chat interface, so **nobody can answer an approval prompt**. Vibe denies any tool call that needs approval and reports it on `stderr`. You have two ways to let a run do real work:

- `--auto-approve` (alias `--yolo`) approves every tool call. Use it in disposable environments.
- A [custom agent](/lessons/agents) whose allowlist covers what the run needs, plus `--enabled-tools` to switch off everything else:

In `vibe-todo`, the `builder` agent from the [Agents](/lessons/agents) lesson already has the allowlist:

```toml
# vibe-todo/.vibe/agents/builder.toml (excerpt)
[tools.bash]
allowlist = ["python3 -m unittest", "python3 -m todo", "ls", "cat"]
```

```bash
vibe --trust -p "Run the tests and report any failures." --agent builder --enabled-tools bash
```

`--enabled-tools` disables every other tool in programmatic mode, so this run can run tests but not read or edit files. To let it fix failures too, repeat the flag for the file tools it needs (`--enabled-tools read_file --enabled-tools edit`). The builder already allows edits.

A chained command such as `pytest; rm -rf build` is denied unless every part is allowlisted.

Project config, skills, and agents only load in a <a href="/glossary#trusted-folder">trusted folder</a>, and the trust prompt never appears in programmatic mode. Pass <code>--trust</code> to trust the working directory for that one run.
</div>

## Output formats

| `--output` | What you get |
|---|---|
| `text` (default) | The final answer. |
| `json` | Every message in the session, as a JSON array, when the run ends. |
| `streaming` | One JSON object per message, newline-delimited, as the run progresses. |

With `json`, the last message with `"role": "assistant"` holds the answer:

```bash
vibe -p "Summarize README.md in one line" --output json --trust > out.json
jq -r '[.[] | select(.role == "assistant")] | last | .content[0].text' out.json
```

For a machine-readable report, add `--output-dir DIR`: Vibe writes `DIR/export.json` (version, effective config, token usage, cost, stop reason, outcome) and a copy of the session, however the run ends.

## Limits and exit codes

| Flag | Stops the run when |
|---|---|
| `--max-turns N` | N assistant turns have run. **Recommended** for every scripted run. |
| `--max-tokens N` | Prompt plus completion tokens reach N, subagents included. |
| `--max-price DOLLARS` | Cost reaches the limit, subagents included. |
| `--time-limit SECONDS` | The deadline passes. The session can be resumed later. |

`--max-price` uses the model prices in your config, which can be missing or outdated. Treat it as indicative, not a hard budget.

| Exit code | Meaning |
|---|---|
| `0` | The agent finished. |
| `1` | The run couldn't start (bad flag or config). |
| `2` | The model API or the runtime failed. |
| `3` | The agent stopped early: a limit, a stop, or a refusal. |

Other useful flags: `--model ALIAS` and `--thinking LEVEL` change the model and its thinking level for one run without saving them, and `-c` or `--resume SESSION_ID` continue a saved session.

## GitHub Action

The [mistral-vibe repository](https://github.com/mistralai/mistral-vibe) ships an `action.yml`. It installs Vibe with uv and runs `vibe -p` in your workspace. You set two inputs: `prompt`, and `MISTRAL_API_KEY`, which you pass from a repository secret. The [Automate CI](/exercises/automate-ci) exercise builds a workflow with it.

## Worktrees

Add `--worktree` to keep an unattended run's changes apart from your checkout: the run works in its own [git worktree](/glossary#worktree), and programmatic runs leave it in place for you to review. The next lesson, [Parallel work](/lessons/parallel), covers worktrees in depth.

## Loops and goals

Two commands keep an interactive session working without you typing:

- **`/loop`** schedules a recurring prompt in plain language, for example `/loop every two minutes check the build`. Run `/loop` on its own to open the loop manager: `d` deletes a loop, `n` adds one. Loops only run while the session is open and idle.
- **`/goal <objective>`** gives the session a durable goal, such as `/goal make every test in tests/api pass`. Vibe keeps starting new turns until the goal is done or blocked. Manage it with `/goal edit`, `/goal pause`, `/goal resume`, and `/goal clear`. Pressing `Escape` pauses it. `/goal` is new in Vibe 3.1.3 and doesn't work in programmatic mode.

Learn more about [programmatic mode](https://docs.mistral.ai/vibe/code/cli/work-with-cli#programmatic-mode) and [worktrees](https://docs.mistral.ai/vibe/code/cli/work-with-cli#worktrees).
