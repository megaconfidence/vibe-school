The [model](/glossary#model) is the brain behind Vibe: it reads your prompt, decides which tools to call, and writes the answer. Vibe ships with Mistral models ready to go, and you can switch between them at any time, change how hard the model thinks, or point Vibe at another provider or a model running on your own machine.

## In your project

No new files this time. You'll ask two models (or two thinking levels) the same small question about `vibe-todo`, such as how they would add a `stats` command, and compare the answers. Keep the model out of the project's `.vibe/config.toml`: it's a personal choice, and a project value would override everyone's own setting.


## See which model you're using

In the CLI, the top border of the input box shows the active model and its [thinking level](/glossary#thinking-level), for example `mistral-medium-3.5[medium]`. Click the model name to open the picker.

For more detail, run `/status`: it shows the model, the provider, and which credential source is in use.

## Change the model and thinking level

<SurfaceTabs>
<SurfaceTab surface="cli">

- `/model` opens the model picker. Press `/` to search the list.
- `/thinking` picks the thinking level for the current model.

Both pickers give you two ways to confirm:

| Key | Effect |
|---|---|
| `Enter` | Saves the choice to your config. New sessions use it too. |
| `s` | Uses it for this session only. |

`/model` saves to `active_model` in `~/.vibe/config.toml`. A session pins its model when you send the first message, so a resumed session keeps the model it last ran on.

</SurfaceTab>
<SurfaceTab surface="vscode">

`/model` and `/thinking` aren't slash commands in the extension. Change the active model or reasoning level from the extension's interface instead. The extension shares the CLI's configuration, so `active_model` and your `[[models]]` presets apply here too.

</SurfaceTab>
<SurfaceTab surface="desktop">

In a Code session, click **Select model** under the input to pick the **Model** and its **Thinking** level. Local sessions share the CLI's core engine, but their tools and prompts can differ. The provider and model settings below are CLI configuration.

</SurfaceTab>
</SurfaceTabs>

Thinking levels include `off`, `low`, `medium`, `high`, `xhigh`, and `max`, depending on what the model supports. More thinking can help with tricky bugs or design questions, but it's slower and uses more tokens. For quick edits, a lower level is usually enough.

## Plans and usage

Vibe Code uses the monthly usage included in your Mistral plan, shared across Studio, the API, and Vibe Code. With a Mistral plan and a Mistral model, the CLI footer shows a **usage gauge** for your organization's monthly Vibe Code usage, if you're allowed to see it:

- Without pay-as-you-go, the gauge turns yellow, then red, as usage nears the limit. Vibe Code can stop until the next billing period.
- With pay-as-you-go on, it reads `PAYG`, and extra usage draws from your prepaid credits.

Pay-as-you-go is off by default. Some Pro plans bought through partners (Google, Apple, Free Mobile, Orange) can't enable it. Run `/whoami` to see your signed-in account, Workspace, plan, and credential source.

## Add another provider

Any model behind an OpenAI-compatible API works. Define a provider and a model preset in `~/.vibe/config.toml`, then select the model by its alias:

```toml
active_model = "devstral-openrouter"

[[providers]]
name = "openrouter"
api_base = "https://openrouter.ai/api/v1"
api_key_env_var = "OPENROUTER_API_KEY"
api_style = "openai"
backend = "generic"

[[models]]
name = "mistralai/devstral-2512:free"
provider = "openrouter"
alias = "devstral-openrouter"
```

Then export the key in your shell (`export OPENROUTER_API_KEY=...`, or `$env:OPENROUTER_API_KEY = "..."` in Windows PowerShell). Keep `active_model` above the first `[[...]]` table, otherwise TOML attaches it to that table. For a model Vibe doesn't know, set `max_context_length` in its preset.

## Run a model locally

For privacy or restricted networks, serve an open model such as [Devstral Small 2](https://huggingface.co/mistralai/Devstral-Small-2-24B-Instruct-2512) yourself. The docs recommend [vLLM](https://github.com/vllm-project/vllm):

```bash
vllm serve mistralai/Devstral-Small-2-24B-Instruct-2512 \
  --tool-call-parser mistral \
  --enable-auto-tool-choice \
  --port 8080
```

[llama.cpp](https://github.com/ggml-org/llama.cpp), LM Studio, and Ollama also work. Vibe has a built-in provider preset named `llamacpp` that points at `http://127.0.0.1:8080/v1` with no API key, so a model preset is all you need:

```toml
active_model = "devstral-local"

[[models]]
name = "mistralai/Devstral-Small-2-24B-Instruct-2512"
provider = "llamacpp"
alias = "devstral-local"
```

Your server must report token usage in streamed replies (`stream_options.include_usage`). To stay fully offline, also set `enable_telemetry = false` and `enable_update_checks = false`. Hardware sizing is in [Using offline models](https://docs.mistral.ai/vibe/code/cli/offline-models).

## Restrict models

`allowed_models` is an allow-list of model name patterns (exact, glob, or `re:` regex). When it's set, only matching models are selectable. It matches the model's `name`, not its alias. Admins usually set it for a whole team: see [Admin config](https://docs.mistral.ai/vibe/code/cli/admin-config).

Every model also has a [context window](/glossary#context-window), a limit on how much it can hold at once. The [Context](/lessons/context) lesson covers how Vibe manages it.

Learn more in the [configuration docs](https://docs.mistral.ai/vibe/code/cli/configuration#providers-models).
