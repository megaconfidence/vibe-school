One agent at a time is fine until you have three small tasks queued up. Vibe can run several agents at once, but only if each one has its own place to work. In this lesson you'll learn the ways to split work in Vibe (worktrees, subagents, sub-sessions, and cloud sessions), when to use each, and how to bring the results back together.

## In your project

Two agents add two commands to `vibe-todo` at the same time, each in its own worktree and branch, then you merge both:

```text
vibe-todo/                  # main checkout, on your main branch
~/.vibe/worktrees/…/stats   # worktree on branch stats: adds cmd_stats + test
~/.vibe/worktrees/…/edit    # worktree on branch edit: adds cmd_edit + tests
```

After the merge, `todo/cli.py` has both commands. Commit everything first: a new worktree starts from a commit, so uncommitted files (like a new skill) wouldn't be in it. In a local-only repository like `vibe-todo`, that's your last commit (`HEAD`). If the repository has a remote, the CLI's `--worktree` starts new branches from the remote's default branch instead, so push your commits first or they won't be in the worktree.


## Why agents step on each other

Two sessions started in the same folder edit the same files. If both touch `README.md`, the last write wins, and a half-finished change from one session can break the other's tests. Opening a second conversation doesn't help: separate conversations share the same checkout.

The fix is a [worktree](/glossary#worktree): a second checkout of the same repository, in its own folder, on its own branch. Worktrees share the git history, so merging later is ordinary git.

<div class="callout">
Worktrees isolate <strong>files</strong>, not everything a task uses. Dependencies, environment variables, external services, and server ports may still need separate setup. Two development servers can't both use port 3000 just because they run in different worktrees.
</div>

## Which tool for which job

| Job | Use | Where |
|---|---|---|
| Two tasks that edit the same repo on your machine | Worktrees | CLI `--worktree`, Desktop **Worktree** |
| A read-only investigation that would flood the context | [Subagents](/glossary#subagent), such as `explore` | CLI, VS Code, Desktop |
| One big task split into visible, coordinated conversations | Sub-sessions (pair with worktrees if they edit) | Desktop |
| Tasks that don't need your machine and should end in a PR | Cloud sessions, one sandbox each | Code Web, Desktop **Cloud** |
| The same unattended task in a script or CI | `vibe -p` with `--worktree` | CLI (see the previous lesson, [Automation](/lessons/automation)) |

## Worktrees

<SurfaceTabs>
<SurfaceTab surface="cli">

Start a session in its own worktree with `--worktree`:

```bash
vibe --worktree parser-tests
```

Vibe creates the worktree under `~/.vibe/worktrees/` (or `$VIBE_HOME/worktrees/`) on a branch named `parser-tests`, or reuses it if it already exists. `--worktree` also trusts the worktree for that run, so project config loads without `--trust`.

Leave out the name and Vibe names the worktree after your prompt (or picks a random slug), on a branch with a `vibe/` prefix. Put the prompt first, because `--worktree` reads the next argument as the name:

```bash
vibe "Fix the login bug" --worktree
```

To work on two things at once, open two terminals in the repository and start one session in each:

```bash
# terminal 1, in vibe-todo
vibe --worktree stats

# terminal 2, in vibe-todo
vibe --worktree edit
```

**Cleanup.** When an interactive session ends, Vibe removes a worktree it created in that run if it holds no changes, and asks you otherwise. Worktrees it reused, and branches that already existed, are kept unless you confirm their removal. Programmatic runs (`-p`) always keep the worktree. `-c` and `--resume` combine with `--worktree` to pick a session back up inside that worktree.

Two settings in `~/.vibe/config.toml` control worktrees:

| Key | Default | What it does |
|---|---|---|
| `worktree_limit` | `15` | Maximum number of recent Vibe-managed worktrees kept locally |
| `worktree_copy_on_write` | `true` | macOS only. Creates new worktrees of a trusted repo from a template checkout under `~/.vibe/worktrees/.templates`, so they use less disk and are created faster. Set it to `false` for regular checkouts |

</SurfaceTab>
<SurfaceTab surface="desktop">

In the **Code** tab, click **New Session**, pick the project, and choose **Worktree** in the **Local / Worktree / Cloud** selector under the input. The session works in its own checkout, so your current one stays untouched. Start a second session the same way for a second task.

You can also ask for a worktree in words, before Vibe edits anything:

```text
Use a new Git worktree for this task. Fix the failing authentication tests,
leaving my current checkout unchanged.
```

Keep a worktree until its changes are committed and delivered, or until you've decided to discard them. Archiving a session doesn't deliver its changes.

</SurfaceTab>
<SurfaceTab surface="code-web">

You don't manage worktrees in Vibe Code Web. Every session runs in its own isolated cloud [sandbox](/glossary#sandbox) with a fresh clone of the repository, and the agent commits to its own branch. A session typically opens a **draft pull request** from a `vibe/...` branch, authored by you.

So running tasks in parallel means starting several sessions, one per task. The number of concurrent sessions per user is plan-dependent, and there are daily quotas (2 sessions a day on Free plans where access is enabled, 100 on paid plans). Sessions are personal: to collaborate, share the branch or pull request.

</SurfaceTab>
</SurfaceTabs>

Whichever surface you use, plain git sees every worktree:

```bash
git worktree list
```

Each line shows a worktree's path, its current commit, and its branch. `git worktree remove <path>` deletes one you no longer need.

## Subagents

A [subagent](/glossary#subagent) is an agent the main agent starts to handle part of a task. It doesn't give you a separate checkout; it gives the main agent extra hands while keeping its [context window](/glossary#context-window) small.

- Vibe ships `explore`, a **read-only** subagent for searching and reading code.
- You can define your own with `agent_type = "subagent"` (see the [Agents](/lessons/agents) lesson).
- The main agent can run several at once: up to 32 by default. `max_subagents` and `max_concurrent_subagents` in `config.toml` change the limits, and `enable_subagents = false` turns subagents off.
- Subagents return **text-only results**, can't ask you questions, and never get broader permissions than the parent.

Ask for them in plain language:

```text
Use subagents in parallel: one lists every command in todo/cli.py and
its test coverage, the other checks which functions touch the file
system. Summarize both, then propose a plan. Don't edit anything yet.
```

<div class="callout">
Subagents don't isolate files. A read-only fan-out is safe; parallel <em>edits</em> belong in separate worktrees.
</div>

### Sub-sessions and subagents in Desktop

Desktop shows delegation in the sidebar and panels:

- A main session can start **sub-sessions**: separate conversations shown as **Started a session** and nested under the main session in the sidebar. They report back with **Received a message from …** entries. Each has its own files, terminal, and **+ → Git Changes**, so select the right conversation before you inspect anything. Ask for separate worktrees when sub-sessions edit the same repo.
- **Subagents** show up as **Started subagent** entries; open one from **Subagents** in the session's top-right panel. Their views are read-only, with a status of `Running`, `Waiting for input`, `Idle`, or `Failed`. To redirect a subagent, talk to the main agent.

## Bring the results together

A finished session isn't a finished task. For each branch:

1. **Review the diff on its own.** `git -C <worktree path> diff`, Desktop's **+ → Git Changes** (**Unified** or **Split**), or the pull request on GitHub.
2. **Run the tests in that worktree.** Two branches can each pass and still conflict once merged.
3. **Commit, then merge or open a PR.** Merge one branch, rerun the tests, then merge the next. If they conflict, ask Vibe to resolve it and explain the resolution, then review it yourself. In `vibe-todo`, `stats` and `edit` both add code to `todo/cli.py` and `tests/test_cli.py`, so the second merge may conflict where both added a function or a test: keep both.
4. **Clean up** worktrees you no longer need.

Parallel work pays off when tasks touch different files. Two agents editing the same function will collide no matter how isolated their checkouts are.
