Real work doesn't stay in one place. You start a task in the terminal, polish it in your editor, review it in a desktop app, and hand the next step to a cloud agent while you do something else. In this exercise, you'll carry one small change through every Vibe Code [surface](/glossary#surface) you have, and end with a draft pull request.

## The flow

```text
CLI                 VS Code               Vibe Desktop           Vibe Code Web
start the task  ->  resume the session -> review Git Changes ->  follow-up in the cloud
/rename it          select code, iterate  commit and push        draft pull request
```

You only need the surfaces you have (at least two). Skip a step if you don't use that surface; your tutor will explain what it would have shown. If you skip Code Web, you finish with a pushed commit instead of a pull request.

## What you'll need

- A small GitHub repository you own and can push to, cloned locally. A throwaway repo is fine.
- At least two of: the CLI, the VS Code extension, Vibe Desktop, and Vibe Code Web at chat.mistral.ai.

## What's shared, and what isn't

- **CLI and VS Code extension** share configuration and [sessions](/glossary#session) through `~/.vibe/`. A session you start in the terminal shows up in the extension's session history, and the other way around.
- **Desktop local sessions** share the CLI's core engine and session logs, so CLI and VS Code sessions appear in Desktop's Sessions list. Desktop doesn't embed the CLI, though, and its tools and prompts can differ.
- **Vibe Code Web** runs in a cloud [sandbox](/glossary#sandbox) that clones your repository from GitHub. It can't see your machine or your local sessions.

<div class="callout">
<strong>Push before you hand off.</strong> Code Web only knows what's on GitHub. If your commit is still local, the cloud session starts without it.
</div>

## Steps on each surface

<SurfaceTabs>
<SurfaceTab surface="cli">

In your repository, run `vibe`, give it a small task, then name the session so you can find it later:

```text
/rename slugify helper
```

The session is saved under `~/.vibe/logs/session/` and scoped to this folder.

</SurfaceTab>
<SurfaceTab surface="vscode">

Open the same folder, open the **Mistral Vibe** tab in the secondary side bar, and click the session history icon. Open the session you started in the CLI. Select a few lines of code: the panel attaches them as a chip such as **slugify.js · L1-6**. Ask a follow-up about the selection and answer the approval card with `1` to `4`.

</SurfaceTab>
<SurfaceTab surface="desktop">

Switch to **Code** (`Shift+Cmd+2` on macOS) and find the session in the Sessions list. Open **+ → Git Changes** and read the diff in **Unified** and **Split** views. Run the tests in **+ → Terminal**, then commit and push.

</SurfaceTab>
<SurfaceTab surface="code-web">

At chat.mistral.ai, open the **Code** tab. Click **New Project**, pick **Using GitHub**, choose your account, search for the repository, click **Next**, then **Create project**. Ask for a small follow-up that builds on your pushed commit and ends in a pull request. Vibe typically opens a **draft** pull request on a `vibe/…` branch, authored by you.

</SurfaceTab>
</SurfaceTabs>

## What you'll learn

- How a session moves between the CLI and VS Code without losing context.
- Where Desktop fits: reviewing local work in one place, with Git Changes beside the conversation.
- Why the handoff to the cloud goes through GitHub, and how to review what comes back.

## Tips

- **Name it early.** A `/rename` title makes the session easy to spot in every list.
- **Keep the task small.** The point is the handoff, not the feature.
- **Expect small differences.** Sharing an engine doesn't mean every command, tool, or setting is the same on every surface.
- **Review before you merge.** The pull request is yours. Mark it ready for review in GitHub when you're happy with it.
