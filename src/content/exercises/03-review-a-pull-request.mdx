A second pair of eyes catches bugs before they ship. In this exercise, you'll check out a pull request and have Vibe read the diff for bugs, missing edge cases, and risky changes. Then you decide which findings are real.

## Check out the branch

With the [GitHub CLI](https://cli.github.com):

```bash
gh pr checkout 42
git diff main...HEAD
```

Or with plain git: `git fetch`, then `git switch <branch>`.

## Ask for a review

Use the `ask` [agent](/glossary#agent) (`Shift+Tab`) so Vibe asks before every tool call, edits included. Then be explicit about what you want:

```text
Review this diff for bugs, missing edge cases, error handling, and risky changes.
For each finding, give file:line, why it matters, and a suggested fix.
Read the surrounding code and run the tests. Don't edit any files.
```

<SurfaceTabs>
<SurfaceTab surface="vscode">

Open a changed file and select the lines you're unsure about. The extension attaches the active file and your selection, so you can ask "Review this diff for edge cases before I open a pull request." Use VS Code's diff and source control views to read the changes alongside Vibe's comments.

</SurfaceTab>
<SurfaceTab surface="cli">

Put the diff in context with a shell command: `!git diff main...HEAD`. The agent sees the command and its output.

With `gh` (or `glab` for GitLab) installed, Vibe tracks the pull request for your branch. The footer shows its status, such as `CI failing` or `conflicts`. Run `/pr` to list the session's pull requests: `Enter` opens one, `c` opens its first failing CI check, and `f` drafts a prompt that fixes what blocks it. Turn this off with `enable_pr_monitoring = false`.

</SurfaceTab>

## Triage the findings

Not every finding is a bug. Sort them into three piles: real bugs, nitpicks, and false positives. Check at least one by reading the code or writing a quick test. A review is only as good as what you verify.

## Tips

- **Give it the "why".** Paste the PR description or linked issue, so Vibe can check the change against its goal.
- **Ask for the test that's missing.** "Which input would break this?" often finds more than "any bugs?".
- **Package your checklist.** If you review the same way every time, turn it into a [skill](/lessons/skills). The worked example in the [Package a team setup](/exercises/package-a-team-setup) exercise ships a `code-review` skill.

More in the [VS Code extension docs](https://docs.mistral.ai/vibe/code/vs-code-extension/work-with-extension) and [Commands and shortcuts](https://docs.mistral.ai/vibe/code/cli/commands-shortcuts).
