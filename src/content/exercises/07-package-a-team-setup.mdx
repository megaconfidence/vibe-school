In the Code lessons you built a full Vibe setup for `vibe-todo`, one piece at a time. In this exercise you bring that setup to a repository you actually work on, adapted to its stack and its team, so anyone who clones it and trusts the folder gets the same agents, skills, instructions, and hooks.

## The layout

The same shape as `vibe-todo`, in your own repository:

```text
my-project/
├── AGENTS.md              # instructions for every session in this project
└── .vibe/
    ├── config.toml        # project choices (default_agent, tool permissions, MCP servers)
    ├── hooks.toml         # project hooks
    ├── hooks/             # scripts your hooks call
    ├── agents/
    │   └── reviewer.toml  # custom agent or subagent
    └── skills/
        └── add-endpoint/
            └── SKILL.md   # a workflow from your team, also a /add-endpoint command
```

| Piece | What it gives your team | Lesson |
|---|---|---|
| `AGENTS.md` | Shared rules: stack, test command, conventions | [Instructions](/lessons/instructions) |
| `.vibe/config.toml` | Project settings that override each user's `~/.vibe/config.toml` | [Configuration](/lessons/configuration) |
| `.vibe/skills/` | Workflows anyone can run with `/skill-name` | [Skills](/lessons/skills) |
| `.vibe/agents/` | Custom agents and subagents with their own tools and permissions | [Agents](/lessons/agents) |
| `.vibe/hooks.toml` | Commands that run at points in the session, like a formatter after each edit | [Hooks](/lessons/hooks) |

<div class="callout">
All of this loads only in a <a href="/glossary#trusted-folder">trusted folder</a>. The first time a teammate starts Vibe in the repo, the CLI asks them to trust it. Tell them in your README, and remind them to review <code>.vibe/</code> like any other code before trusting it.
</div>

## Adapt, don't copy

`vibe-todo` is a pattern. Your repository needs its own test command, its own conventions, and workflows your team already repeats. Start small: `AGENTS.md` plus one skill is often enough for a first pull request. If you skipped the course project, the [agents, skills, and instructions example](/examples/agents-skills-instructions) shows the same layout, with a README that explains how each piece points to the others.

## Keep secrets out

`.vibe/config.toml` is committed, so never put a key in it. For an MCP server that needs one, point at an environment variable with `api_key_env`, and let each teammate set it themselves.

## Test it like a teammate

Start a fresh session in the folder and check that:

- the custom agent shows up when you press `Shift+Tab` (or in the **Session mode** menu in VS Code),
- the skill appears in the `/` picker,
- the hook runs when it should.

The CLI and VS Code extension read the same project files. Desktop local sessions share the CLI's core engine, but their tools and prompts can differ, so test there too.

## Going further: a plugin

When the same skills and subagents are useful across many repositories, package them as a [plugin](/glossary#plugin): a folder with a `plugin.json` manifest, a `skills/` folder, and Vibe-specific parts under `ai.mistral.vibe/`. Project plugins go in `.vibe/plugins/<plugin>/`, user plugins in `~/.vibe/plugins/<plugin>/`. Run `/plugins` to check what loaded and `/reload-plugins` to pick up changes. See the [Plugins](/lessons/plugins) lesson.

For the bigger picture (admin config, the Admin Panel, and a rollout checklist), see the [Team rollout](/lessons/team-rollout) lesson. More in the docs on [configuration](https://docs.mistral.ai/vibe/code/cli/configuration), [trusted folders](https://docs.mistral.ai/vibe/code/safety-approvals-permissions#trusted-folders), and [plugins](https://docs.mistral.ai/vibe/code/cli/plugins).
